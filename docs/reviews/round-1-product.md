## 发现

### P1 — H3 “候选”表述可能允许悄然替换首个验收模型

- 位置：workflow「原始目标与完成条件」。
- 需求：用户指定 H3 视频生成，PRD 的最终硬件验收也包含 H3。
- 发现：workflow 称 H3 为“首个候选模型”，但没有紧邻明确说明替代模型只能验证基础设施。研究文档对此写得正确，但治理文档应避免范围分歧。
- 建议：统一成“首个目标模型，许可与设备可行性待验证”；写明更换最终验收模型需要用户明确变更目标，不能由实现自行降级。
- 责任：主代理/治理文档作者。

### P1 — 审查门禁尚缺撤销、编辑与失败优先规则

- 位置：workflow「共享账号限制」。
- 需求：其他 agent 实际审查最新 SHA 后才能合并；未解决阻塞不得被旧批准掩盖。
- 发现：已正确声明共享身份限制和精确 SHA，但缺少结构化记录 schema，以及评论被编辑、删除、撤销或同 SHA 后续提出阻塞意见时的判定。
- 建议：在 CI spec 定义 author/reviewer/SHA/结论/引用、信任来源与事件触发；使用最新有效结论，无法读取证据时 fail closed；任何待处理阻塞都禁止合并。执行测试应覆盖 stale SHA、自审、非维护者、格式错误、撤销与评论删除。Gate 验证流程记录，不宣称密码学上独立的 agent 身份。
- 责任：主代理/架构与 QA。

### P1 — 无真机环境下需将开发门禁与最终能力门禁分开

- 位置：workflow「测试与交付」「当前硬件事实」；研究「证据阶梯」。
- 需求：iPhone 不能被排除最终目标；不可用设备也不能阻止所有基础设施开发。
- 发现：文档已正确记录 NOT RUN，但尚未定义机器可读的证据状态和 release gate。若后续只检查默认 CI 全绿，可能把所有硬件测试跳过后误标稳定完成。
- 建议：规格定义每项硬件验收 PASS/FAIL/NOT RUN 及证据附件，开发 PR 允许相关缺口显式存在，最终能力发布必须检查全部必需真机项 PASS。本机缺 Xcode 与手机暂不可测试应成为 backlog 与未完成证据，不能改写支持声明。
- 责任：架构与 QA；发布流程作者。

### P2 — 研究中的 Mac 基线与当前已核实事实不一致

- 位置：feasibility 第 1 节与第 8 节。
- 发现：仍写 16GB 待确认、需补充 Mac 内存，workflow 已记录 `hw.memsize = 17179869184`。研究也应记录手机当前无法真机测试和完整 Xcode 缺失，避免规划误用可访问设备。
- 建议：引用设备清单作为单一事实来源，注明采样日期；物理内存已知不等于可用内存预算已测量。
- 责任：研究作者。

### P2 — 最终“两台手机”要求应在执行矩阵固定

- 位置：研究第 7 节第 5 项，先一台再两台的递进描述。
- 需求：PRD-05 为两台 iPhone 参与同一目标任务并执行模型计算。
- 发现：递进路线合理，但如果测试矩阵只固化“一台 iPhone”，中间里程碑可能被误当最终验收。
- 建议：保留三设备 milestone，并额外定义四设备最终测试与每台手机贡献证明；贡献须是影响推理结果的模型运算，不能只有心跳、转码或控制界面。
- 责任：QA。

## 已确认正确的决策

### 追加 P1 — PRD 生命周期、资源控制和用户操作缺少规格追踪

- 位置：spec REQ-001..017；test-plan 需求矩阵。
- 发现：manifest 哈希验证不覆盖 PRD-08 下载恢复/本地导入/卸载；资源规划不覆盖 PRD-11 用户资源和电池上限、数据删除；PRD-14 干净环境安装复现、暂停/继续也缺明确测试。它们影响真实用户能否使用，不能隐含为接口原型之外的可选项。
- 建议：新增需求和对应测试，或给出精确现有映射；需覆盖活跃任务阻止卸载、损坏下载恢复、删除范围、暂停持久状态和安装复现。
- 责任：架构与 QA。

### 追加 P1 — “只重算未提交片段”与步骤检查点恢复语义存在歧义

- 位置：spec REQ-011、第 6 节。
- 发现：若片段结果只在内存已提交，协调器重启后从最近完整去噪步骤恢复，需要重算后来已提交但未持久化的片段。当前绝对禁止重算已提交片段与此不兼容。
- 建议：定义片段输出是否持久化、检查点恢复 epoch、至多一次对外提交范围。允许基于检查点重算而不产生重复可见结果；加恢复故障测试。
- 责任：架构与 QA。

### 追加确认 — 两台手机最终测试已经存在

test-plan 已提供 E2E-03 两台 iPhone 同次生成，因此上文“两台手机矩阵”发现已由初稿测试设计解决；后续检查实现和真实执行证据，不再要求重复设计。

- 多设备与容量收益是核心；没有把目标换成单机优化。
- 不把统一内存与独立显存混加；加载期峰值、激活与工作区必须计入。
- iOS 不等于桌面 Python；前台先行，后端能力需要真机验证。
- 同一精度与配置对照；人为降低单机预算的结果只能称受限预算实验。
- H3 的模型、许可、音视频状态与实际 block 边界都要核验；不直接套用 LLM 框架结论。
- 同 GitHub 账号不能产生独立账号批准；流程诚实记录非作者审查。

## protocol-v1 追加审查

已阅读主代理编写的 `docs/spec/protocol-v1.md`，这是非作者审查。

1. **P1，D-03 与 system-spec §4 流控冲突。**前者限制两条数据流，后者限制两个在途块；两条流仍可无限积累 buffer。统一总缓冲字节预算、每流块上限与背压语义，并测试多流总峰值。
2. **P1，D-05 幂等优先级不明确。**“deadline 到期拒绝”与“重复已提交结果返回已有 commit”在超时后重发同结果时冲突。应先判断已提交且结果摘要一致的重发并返回已有提交，再拒绝未提交的过期结果；不一致结果返回冲突。
3. **P1，D-02 制品授权须防止跨任务复用带来泄露。**内容寻址复用不代表授权继承。相同 digest 在不同作业内仍需分别授权，节点不得靠已知 digest 获取其他作业的数据；撤销/过期租约应更新访问许可。需明确授权生命周期与测试。
4. **P2，D-02 无 body 请求。**“Content-Length 必需”需明确适用于携带 body 请求和响应，GET/DELETE 无 body 的处理避免 Python/Swift 标准客户端互操作歧义。
5. **P2，张量身份位置不一致。**system-spec §4 要求张量信封含 job/attempt/fragment，protocol-v1 使用任务包裹内容制品。后一设计合理，但必须同步两个文档并保证先授权 task 再访问 artifact。
6. **P2，暂停与恢复。**已定义 resume，没有 pause 路由或 paused 状态；需在完整契约补齐或明确延后条款，并保留产品最终验收。resume 不能让 cancelled/succeeded 回到运行。
