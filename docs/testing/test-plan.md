# 测试计划与需求追踪

状态：设计初稿，版本 0.1，2026-10-06。规范来源：[system-spec.md](../spec/system-spec.md)。此文件定义验收，不表示任何测试已经执行或通过。

## 1. 测试先行流程

每个实现 PR 在描述中关联需求 ID、spec 版本、测试文件和本地 red/green 证据。先提交或记录必然失败且失败原因对应缺失行为的测试，再实现最小变更使其通过，再重构并重跑受影响检查。测试必须观测输入输出和状态不变量，避免仅断言私有函数被调用。文档类变更运行链接/schema/格式检查；不能为文档机械制造无价值测试。

作者智能体提交 PR，另一个智能体读取 diff、需求及证据并独立运行相关验证，给出问题或批准。作者修复后需重新审查变更部分。GitHub 若只有同一个用户 token，无法用作者身份提交正式 APPROVE；不得把普通评论称为 GitHub approval。应记录 agent 独立审查证据，并将账号限制报告主协调器，按可验证的仓库策略解决，不冒充另一账号。

## 3. 数值正确性

小模型 fixture 必须为真实运算图：确定性权重的小型 Transformer，包含线性层、激活、归一化、attention、残差和条件输入；输入至少覆盖非方形形状、非零 seed 和多次迭代。CPU float32 完整执行为参考；跨设备路径执行相同权重和相同图，不能将预计算答案硬编码到手机或测试替身。留出仅在验证时使用的输入，防止金样本记忆式实现。

对每个 profile 先独立记录单机后端误差，再预先冻结跨设备误差门槛。小模型 float32 起始门槛 `atol=1e-5, rtol=1e-4`；float16 候选门槛 `atol=1e-2, rtol=1e-2`，必须以误差研究确定后才能验收，不能在失败后只扩大门槛。检查形状、有限值、最大绝对误差、相对误差及输出差异；量化比较以相同量化语义为参照。

H3 真实组件和端到端需定义专属误差门槛：跨 CUDA/MPS/iOS 的浮点差异不保证逐像素视频一致。先比较单步/多步 latent 与组件输出，确认差异来源，再检查最终视频解码、无 NaN、有效动态范围、时间连贯性与固定提示词的人工核验。可播放文件单独不能证明正确生成或模型等价。取消、恢复也检查结果语义，不能只看状态字段。

## 4. 故障与资源测试

在传输头、流中间、计算中、结果发送后未确认、检查点发布前后、协调器重启等时点注入故障。验证 epoch 内片段结果和最终产物均无重复提交、不读取半张量、不执行不同 manifest、无孤立临时文件持续增长、旧会话无法覆盖新作业。步内临时输出丢失时必须创建新 recovery_epoch，允许重算但旧 epoch 迟到结果被拒绝。注入磁盘满和内存预算拒绝必须保持上一检查点可读。

构造慢节点和受限网络，测量 sender queue/receiver buffer，不得随着视频步数无限增长。持续运行覆盖完整目标视频时长；手机热降频后允许变慢但不允许静默丢步骤。手机系统级挂起/内存终止需实机复现，模拟事件只能验证错误分支。

安全测试包含未认证执行/张量请求、错误证书、过期配对 token、重放、路径穿越 manifest、巨大 shape、整数溢出、恶意序列化。系统不接受用户远程提交可执行代码，避免把模型执行协议变成通用远程命令接口。

## 5. CI/CD 门禁

每个 PR 必需检查：Linux、Windows、macOS 的桌面 CPU 单元和进程集成测试，schema/manifest/协议金样本检查，静态检查；macOS runner 上编译 iOS 目标并运行可在模拟器执行的协议与序列化测试。最终具体 runner、Xcode 与 Python 版本锁定到仓库配置，并记录支持矩阵。公共托管 macOS runner 的 GPU 能力不能推定等于用户的 M4；iOS 模拟器不能证明 iPhone GPU/内存/后台行为。

CUDA/MPS/iPhone 真实算子、H3 下载/执行和最终视频测试单列硬件验收工作流，不用 mock 报绿冒充覆盖。无可用设备时显示未运行及原因。发布门禁同时要求普通 CI 和对应硬件证据，硬件证据绑定 commit SHA、manifest digest 和 profile；旧证据不能替新代码背书。

CD 先提供可追踪构建产物与校验值；未配置 Apple 签名时只交付编译产物与签名部署说明，不声称可直接安装或已经部署 iPhone。发布包不得包含凭证、用户提示词或无再分发许可的权重。依赖固定版本，模型按来源与哈希下载。

开发PR允许真机证据明确为 `NOT_RUN`；目标能力发布要求所有指定设备及H3必需项 `PASS`。证据记录字段固定为 `test_id, requirement_ids, commit_sha, manifest_digest, profile_digest, device_class, status, reason, artifact_sha256`，status只能是 `PASS|FAIL|NOT_RUN`。没有artifact、SHA不符、未知状态、缺少任一必需设备均拒绝最终能力发布。dev构建不得带正式支持声明。

FLOW门禁负例必须覆盖同agent自审、陈旧SHA、无维护权限评论、格式错误、编辑/删除/撤销批准、新增阻塞意见、读取评论失败。任何未知或无法读取证据均fail closed；CI不执行评论中的命令。测试基于实际GitHub payload fixture，合并前重新校验当前HEAD及checks，不把前一提交的绿灯复用。

## 6. 端到端验收顺序

1. 桌面两进程通过真实小模型拼接、故障恢复和完整协议测试。
2. Windows 4060 与 Mac M4 真机通过同样小模型；记录后端/资源差异。
3. 加入一台 iPhone 执行真实模型片段，再加入第二台；完整输出依赖各节点返回的真实计算结果。
4. 在目标 H3 真实组件上验证 CUDA/MPS/iOS 运算、量化、峰值内存和切分边界；不适配的算子列入阻碍并实现/研究后重验。
5. 完整 H3 指定 profile，在局域网断开互联网后生成视频；检查每设备贡献、输出、资源和恢复。
6. 固定模型/profile/卸载策略做单节点容量对照；若单节点也成功，应如实报告仅证明分布式执行，继续寻找符合目标且硬件可行的容量扩展配置。
7. 发布前对冻结 commit 完整回归；独立 reviewer 按 REQ-001 至 REQ-021 审计证据，未覆盖项保留未完成。

## 7. 证据模板

每次验收记录日期、commit SHA、PR、审查智能体、机器/系统/运行时版本、manifest/profile digest、原始命令、退出码、日志与输出文件校验值、通过/失败/未运行、已知限制。真实设备测试另附节点 ID 与片段对应、峰值 CPU/GPU/统一内存、传输字节、总时长和最终视频。测试结果文档必须明确区分“已执行证据”与“计划”。
